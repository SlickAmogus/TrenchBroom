# Gap Check / Feasibility Verdict

## Verdict

The plan is feasible with no showstopper. The six reports plus my verification scans fully specify the v1 read direction (IPD+TIM -> TrenchBroom): byte layouts are pinned by pc_port/src/ipd_reformat.c + lm_reformat.c, and I confirmed disc-wide (all 493 BG IPDs + 5 TEST IPDs + all PLMs, 441,275 prims, 1,734 materials) that every writer-relevant invariant holds: prim clut is always a multiple of 64 (pure CLUT-row*64, max row 15), the on-disc tpage byte is always 0, all material base fields (field_C/unk_D/field_E..field_16) are always 0, header bytes 0x0B-0x13 are always 0, filename cell coords always match header bytes 2-3, triangles are ALWAYS encoded as a repeated vertex index (zero occurrences of the 0xFF sentinel in map data), the collision subcellRanges array always has countX*countZ+1 entries with terminator {field_24,field_26} in every retail IPD, all exterior IPDs are <=45056 B and the largest interior (ERFC00.IPD, 79,616 B) fits the 90112 B slot with ~12% headroom. I also resolved the lighting-slot ambiguity: every unkPtr_14 byte on disc is a vertex index (< vertexCount, 830k+ slots, zero exceptions) grouped so that sum(s_Normal.count)==lightingSlotCount, with the mode split (MAP_EFFECTS_INFOS field_0 byte 2: mode 0 uses raw bytes as darkness, mode 1 treats them as vertex indices and overwrites, mode 2 ignores them) being purely a runtime rendering concern -- a writer must always emit vertex indices. ER vs ER2 MAP_INFOS rows are byte-identical (src/bodyprog/sys/map_info.c:478-479), and BTT_*.IPD test files are retail-format (magic 0x14, valid LM v6) usable as geometry parser fixtures but NOT as collision fixtures (their ranges terminator violates the retail invariant). Remaining risk is concentrated in the write-back path (goal b), not the converter (goal a): collision ptr_18 semantics, draw-structure regeneration algorithms, and the new-cell file-table limitation are the open items listed below.

## Critical gaps

### Write-back only: exact geometric semantics of s_IpdCollisionData_18 records (SVECTOR3 offset + q7_8 field_8, the 'point/cylinder-like obstacles') and the authoring meaning of s_IpdCollSubcell's 2-bit idA/idB event-flag groups per map.

- **Why blocking:** Blocks the collision half of map2ipd (re-packing edited geometry with valid collision); does NOT block the v1 IPD->TrenchBroom read converter, which can pass collision through opaquely or render it read-only.
- **Where to look:** src/bodyprog/collision/collision.c func_8006C3D4/func_8006C45C (ptr_18 consumption) and func_8006B318 at collision.c:1354-1357 (flag index (idA*4)|idB); cross-check against belek666's external sh_ipd2obj; survey retail IPDs statistically (my scan script at scratchpad/ipd_scan.py is extendable).

### Write-back only: the authoring algorithm for the IPD draw structures -- how to partition edited geometry into modelBuffers (AABBs + visibility rects), the 5x5 subcell draw table {start,count} pairs, and modelOrderList ordering.

- **Why blocking:** Consumption semantics are fully documented (Ipd_ChunkDraw, bodyprog_80040B74.c:2389-2544) but no report gives a generation recipe; map2ipd must synthesize these or edits won't cull/draw correctly. Not needed for the read direction.
- **Where to look:** Reverse the retail data: for a few IPDs, compute which subcell rects/AABBs enclose which model instances and infer the packing rule; Ipd_ChunkDraw + Gfx_ChunkSubcellVisibleCheck (bodyprog_80040B74.c:2546-2581) define the correctness condition (conservative superset is safe: one buffer covering the whole cell, all 25 draw-table entries = {0, modelOrderCount}).

### Decision (data all known): the SH->TrenchBroom coordinate convention -- scale factor (SH geometry is Q23.8, 256 units per world unit, one cell = 10240 Q8) and the +Y-down (PSX) to +Z-up (TB) axis mapping, plus whether ipd2map bakes model-instance matrices (Q12 rotations) into world-space brushes or represents instances as point entities.

- **Why blocking:** Every converter line depends on it, and flattening instanced models into unique brushes can blow the 45056 B exterior slot cap on write-back; instances-as-entities preserves the size budget but needs the glb/obj model pipeline from day one.
- **Where to look:** No file answers this -- it is a design decision to record before coding. Inputs: include/game.h:29 (CHUNK_CELL_SIZE Q12(40.0)), include/bodyprog/math/fixed_point.h, s_IpdModelInstance layout in pc_port/src/ipd_reformat.c:57-79, TB grid snapping (powers of 2).

### Goal (b) infrastructure: adding NEW IPD cells (names absent from g_FileTable) requires regenerating filetable.c.USA.inc + fileenum.h.USA.inc and rebuilding the exe, or extending Map_MakeIpdGrid's SH_PC_PORT block to scan gamedata/load/BG/; byte-replacement of existing cells is capped at the original file's sector-aligned size.

- **Why blocking:** Defines the v1 editing contract: same-cell edits <= original size work today via allow_loose_files; anything bigger or new needs a port-side change. Must be stated in the converter's output validation.
- **Where to look:** src/main/fsqueue_3.c:227-383 (loose override + bufSize from blockCount at :292), src/bodyprog/gfx/bodyprog_80040B74.c:846-895 (Map_MakeIpdGrid). Concrete size table now known from my scan: all exteriors <=45056, largest interior 79616/90112.

### Minor render-fidelity item: how the editor preview should shade prims whose isTransparent bit is set -- map material slots load with BlendMode_Additive (bodyprog_80040B74.c:2244,2249), which TrenchBroom cannot reproduce (PNG alpha only approximates it).

- **Why blocking:** Only affects in-editor visual approximation, not data round-trip (the IPD keeps original TIM references and the bit is preserved in surfaceFlags). Listed because the two reports imply different PNG alpha recipes and the tim2png converter must pick one documented rule (raw 0x0000 -> alpha 0; STP-set -> flag the material, not alpha 0.5).
- **Where to look:** pc_port/PsyCross/src/render/PsyX_render.cpp:835-839, 970-975 (decode + discard rules) and bodyprog_80055028.c:4009 (code |0x3C with ABE bit).

## Contradictions found and resolved

- unkPtr_14 / prim.field_10 semantics: ipd-map-geometry called the bytes vertex indices but left the mode-0 'baked brightness' possibility open; textures-tim-vram called it a 'baked per-vertex shading table' and its recipe step 5 ('modulate by unkPtr_14[field_10[k]], treat 128 as 1.0') is wrong. RESOLVED by disc-wide scan + code read: every on-disc slot byte in every IPD and PLM is a vertex index (< vertexCount; sum of s_Normal.count == lightingSlotCount; zero exceptions in ~830k slots). Mode 1 (func_80057658, bodyprog_80055028.c:1893) reads them as vertex indices and overwrites scratch with computed darkness; mode 2 (func_80057A3C:2027) ignores them entirely; mode 0 leaves the switch at :1805-1817 a no-op so the draw block (:3010-3056) consumes the raw vertex-index bytes as darkness (>=8 -> 0x1000-v*32, <8 -> constant 0x3C) -- a runtime quirk, not an authoring variant. A writer must always emit vertex indices grouped by normal.
- Triangle encoding emphasis: ipd-map-geometry's checklist allows 'idx3==0xFF or repeated index'. Scan result: 0 of 441,275 map prims use 0xFF; all 45,327 triangles use a repeated index. The 0xFF path exists only in engine code (lit-model path); ipd2map/map2ipd should use repeated-index exclusively.
- ER vs ER2: disc-inventory flagged the two MAP_INFOS rows as an open question; pcport-loading treated them as distinct. RESOLVED: rows 478-479 of src/bodyprog/sys/map_info.c are byte-identical ({NO_VALUE, "ER", TwoActiveChunks|Interior, NULL, SPEED_ZONES_ER}); there is no functional difference.
- BTT test fixtures: disc-inventory questioned whether TEST/BTT_*.IPD are retail-format. RESOLVED: magic 0x14, same header layout (modelInfoOff 0x188), valid LM v6 -- fine as geometry parser fixtures; BUT their collision blocks violate the retail subcellRanges terminator invariant (field_2 != field_26, e.g. BTT_0000: 0 vs 68), so do not use them to validate a collision re-packer, and ipd-map-geometry's 'verify +1 terminator across all files' is now verified for all 468 retail collision-bearing IPDs.
- Collision location: disc-inventory listed 'does IPD embed collision or is it in the VIN overlay?' as open; ipd-map-geometry had already answered it (308-byte block at file offset 0x54, self-contained). Not a real contradiction, just an unpropagated resolution.
- Minor count discrepancies: textures-tim-vram says disc_extract/TIM/ has 211 files and BG/ has '~470' IPDs; disc-inventory says 207 TIMs and 493 IPDs. 493 is correct (verified by glob); the TIM/ delta is stray working dirs. Also textures-tim-vram's interior-material claim and pcport's dynamic interior tpage note agree in substance (key offline tools by material name, never runtime slot).
- Semi-transparency display recipe: textures-tim-vram says isTransparent map prims blend ADDITIVELY (material slots registered with BlendMode_Additive) while trenchbroom-extensibility's v1 plan maps 'STP -> alpha' in tim2png; both are self-consistent in their own domain but the converter spec must not conflate them (STP bit selects semi-transparency per texel; the BLEND MODE for map terrain is additive, not alpha-average).
